## 一、调研结论摘要

| 问题 | 结论 |
|---|---|
| 网页能否直接读 Apple 健康？ | **不能。** HealthKit 是 iOS 系统级私有框架，只有原生 App / 快捷指令能读；普通网页（含 PWA）拿不到 |
| 有没有变通方式？ | **有两条可行路径**：① 系统「导出所有健康数据」→ 导入 XML ② 快捷指令定时导出 JSON 自动投递 |
| 是否需要一个新页面？ | 需要，但**同一个网页内**即可（第二个视图，像 App 的 Tab 切换），主页面布局不动 |
| 数据是否可靠？ | 「活动能量」在 Apple Watch 上较准，**只带 iPhone 时常常偏低甚至缺失**，方案里必须据此降级 |
| 减脂模型是否成熟？ | 是，BMR/TDEE 公式稳定（Mifflin-St Jeor 等），「摄入 − 消耗」的能量平衡是标准做法 |

## 二、减脂热量计算的科学基础

### 1. 能量平衡总式

```
每日热量缺口 = 总消耗 TDEE − 饮食摄入
预期减脂   ≈ 累计缺口 ÷ 7700 kcal   （1 kg 脂肪 ≈ 7700 kcal）
```

例：每天缺口 500 kcal → 一周约 3500 kcal → **约 0.45 kg/周**，这是公认比较安全、能保住肌肉的速度。

### 2. TDEE 的组成

```
TDEE = BMR（基础代谢） + TEF（食物热效应，约 10% 摄入） + EAT（运动消耗） + NEAT（日常活动）
```

Apple 健康能直接提供其中两项，这比传统「活动系数估算」精确得多：

| Apple 健康指标 | 对应成分 | HealthKit 标识符 |
|---|---|---|
| 静息能量（Resting Energy） | 接近 BMR | `basalEnergyBurned` |
| 活动能量（Active Energy） | EAT + NEAT | `activeEnergyBurned` |
| 步数 / 步行距离 | NEAT 参考 | `stepCount` / `distanceWalkingRunning` |
| 体重 / 体脂率 / 去脂体重 | 公式输入 | `bodyMass` / `bodyFatPercentage` / `leanBodyMass` |

> ⚠️ 注意：`basalEnergyBurned` 在 Apple Watch 上通常是设备估算的静息消耗，与「BMR 公式值」不应简单叠加（有重叠）。方案里两者分开呈现，不要让用户以为要相加。

### 3. BMR 公式选择（三选一，可自动择优）

| 公式 | 表达式 | 适用 |
|---|---|---|
| **Mifflin-St Jeor**（推荐默认） | 男：`10W + 6.25H − 5A + 5`<br>女：`10W + 6.25H − 5A − 161` | 一般人群最准（W=kg, H=cm, A=岁） |
| **Katch-McArdle** | `370 + 21.6 × LBM(kg)` | **有体脂率时更准**，Apple 健康能读到体脂率 |
| **Schofield**（WHO 推荐） | 按性别+年龄段系数，见 WHO 报告 | 亚洲人群可靠性与效度较高 |

自动择优逻辑：**能读到体脂率 → 用 Katch-McArdle；否则用 Mifflin-St Jeor**，并在界面上标明当前用的是哪个。

### 4. 无 Apple 健康数据时的降级方案（活动系数）

| 等级 | 系数 | 描述 |
|---|---|---|
| 久坐 | 1.2 | 办公室，几乎不运动 |
| 轻度 | 1.375 | 每周 1–3 次轻运动 |
| 中度 | 1.55 | 每周 3–5 次中等运动 |
| 高度 | 1.725 | 每周 6–7 次高强度 |
| 极高 | 1.9 | 体力劳动 / 一天两练 |

### 5. 目标缺口与安全边界

```
建议缺口 = clamp(TDEE × 0.20, 300, 750)     // 取 TDEE 的 20%，并限制在 300~750
目标摄入 = max(TDEE − 建议缺口, 安全下限)
安全下限 = 男 1500 kcal / 女 1200 kcal       // 低于此值需提示风险
```

- 每周减重超过体重的 **1%** 视为过快，需警告
- 减脂期蛋白质建议 **1.6–2.2 g/kg 体重**（保肌），可在现有目标设置里加提示

## 三、Apple 健康数据怎么进到网页

### 路径 A：系统导出（兜底，零依赖，先做这个）

1. iPhone「健康」App → 右上角头像 → **导出所有健康数据**
2. 生成 `导出.zip`（含 `apple_health_export/导出.xml`，**常达数十至数百 MB**）
3. 在「文件」App 里解压 → 得到 XML
4. 本应用新增「导入健康数据」→ 选择该 XML → 解析出每日汇总

**XML 结构（已确认）**：

```xml
<Record type="HKQuantityTypeIdentifierActiveEnergyBurned"
        sourceName="Apple Watch" unit="kcal"
        creationDate="2026-10-01 20:11:03 +0800"
        startDate="2026-10-01 08:00:00 +0800"
        endDate="2026-10-01 08:30:00 +0800" value="215.3"/>
```

- 优点：**完全可行、不花钱、不装东西**，今天就能实现
- 缺点：手动、文件巨大（需**分块流式解析**，不能整文件读进内存，否则页面会卡死）
- 解析目标：按天聚合 `activeEnergyBurned`、`basalEnergyBurned`、`bodyMass`、`bodyFatPercentage`、`stepCount`

### 路径 B：快捷指令自动同步（体验最佳，二期做）

iPhone「快捷指令」App 内置 HealthKit 查询能力，可以在设备上读健康数据并写出文件：

```
每天 23:00 自动化
  → 查找健康样本（活动能量 / 静息能量 / 体重，范围=今天）
  → 汇总（求和 / 最新值）
  → 组合成 JSON
  → 存入 iCloud Drive（固定文件名，如 health-latest.json）
  → 或 POST 到某个 Webhook
本应用 → 「从 iCloud 文件导入」读取该 JSON
```

- 优点：**免手动、每天自动**，且只导出汇总值（几十字节，不用担心文件大小）
- 需要实测确认的点：**「查找健康样本」动作的具体名称、参数项、以及能否直接「求和/取最新值」** —— 这些必须在你手机上核对，我不能凭记忆当事实写
- 备选：App Store 上有 `Health Auto Export`、`Health Webhook`、`HealthRelay` 等付费/免费 App 专门做这件事，若快捷指令不顺可用它们替代

### 明确不可行的路径

- ❌ 网页直接调 HealthKit（无此 API）
- ❌ 网页通过 Safari 访问健康数据（隐私限制）
- ❌ 用 HealthKit 的 REST 接口（不存在，只有原生 SDK）

## 五、方案规划（不动主页面布局）

### 页面结构：同一网页内加「第二屏」

```
┌─ 主屏「饮食」（现有布局完全不变）──────────┐
│  顶部日期 + 日历                          │
│  摄入热量                                 │
│  饮食记录（四餐）                          │
│  营养摄入（圆环）                          │
│  ─────────────────────────────────────   │
│  [ 卡片：今日能量平衡（来自第二屏的摘要）]  │  ← 新增一小块
│  [ 查看代谢与消耗 › ]                      │  ← 新增入口
└──────────────────────────────────────────┘
         ↓ 点入口
┌─ 第二屏「代谢与消耗」────────────────────┐
│  ‹ 返回                                    │
│  【身体数据】身高/体重/年龄/性别/体脂率     │
│     → 显示 BMR（标明用的哪个公式）          │
│  【今日能量平衡】                          │
│     总消耗 ████████ 2,150                 │
│     ├ 静息 1,450  └ 活动 520  └ 食物热效应 180 │
│     饮食摄入 ██████ 1,500                 │
│     缺口 −650 kcal  →  预期每周 −0.59 kg   │
│  【趋势】近 14 天：摄入 vs 消耗 双柱 / 折线  │
│  【体重】记录 + 趋势线                     │
│  【健康数据】导入 XML / 从文件导入 JSON     │
└──────────────────────────────────────────┘
```

**为什么放在同一网页里**：现有是单文件 PWA，加第二个视图零成本、离线可用、不用改部署方式。

### 需要新增的数据结构

```js
// 身体档案（localStorage: kcal.body.v1）
{ sex:'male', birthYear:1995, heightCm:175, activityLevel:'light' }

// 每日消耗与体重（localStorage: kcal.burn.v1）
{
  '2026-10-03': { active: 520, basal: 1450, steps: 8210, source: 'shortcut' },
}
// 体重单独存（localStorage: kcal.weight.v1）
{ '2026-10-03': { kg: 72.4, bodyFat: 21.3 } }
```

### 与现有数据的关系（保持向后兼容）

- 现有饮食记录**不动、不改结构**
- 新数据单独存 key，缺失时整个第二屏显示「先去设置身体数据」
- 主屏的「今日能量平衡」卡片在**没有消耗数据时自动隐藏**

### 实施分期

| 期 | 内容 | 风险 |
|---|---|---|
| **P1** | 身体档案 + BMR/TDEE 公式 + 目标缺口计算 + 第二屏界面（用活动系数，无需健康数据） | 低，纯计算 |
| **P2** | 体重记录与趋势；能量平衡用「BMR × 活动系数」近似 | 低 |
| **P3** | **Apple 健康 XML 导入**（分块解析 + 按天聚合），替换近似值为真实数据 | 中，需处理大文件 |
| **P4** | 快捷指令 JSON 导入（自动同步），并给出手机端配置图文步骤 | 中，需真机核对动作名 |
| **P5** | 14 天摄入 vs 消耗趋势图、体重趋势线 | 低 |

## 六、需要在动手前确认的决策点

1. **先做哪条路径？** 建议 P1+P2+P3（公式 + 体重 + XML 导入），能立刻用上且不依赖真机调试
2. **是否接受手动导出 XML 的麻烦？** 若嫌烦，P4 优先（但需要你在手机上配合核对快捷指令）
3. **体重/围度要不要一起记？** 减脂看趋势比看单日数字重要
4. **是否要接入「运动记录」明细**（跑步/力量训练分开），还是只要每日总消耗即可
