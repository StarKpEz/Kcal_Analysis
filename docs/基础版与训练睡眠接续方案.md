# 基础版与训练、睡眠接续方案

更新：2026-10-07，体重同步与睡眠分期版 `2026-10-07.7`。本方案保留现有静态 PWA 与 iPhone 主屏幕使用方式，原 LifeTracker 记账 MVP 保持暂停。

## 当前页面入口

已建立底部“饮食 / 健康”切换。健康页汇总活动能量、静息能量、体重、训练与睡眠；两个栏目共用日期并保留详情及滚动位置。体重使用绿色空心圆折线，按真实日期间距显示近14天称重。

训练会话和每日睡眠支持手动新增/修正。健康JSON入口支持体重日汇总及精简健康样本，睡眠按实际片段去重并展示核心、深度、REM；体重来源与称重时间进入v7完整备份。文件格式见 [健康数据导入格式](健康数据导入格式.md)。已提供 [iPhone 手动创建快捷指令指南](shortcuts-guide.html)，没有签名的一键安装文件，实际单位、分类、来源仍待手机核对。训练会话的快捷指令读取未完成，网页不直接读取HealthKit。趋势暂留代谢详情，顶部模糊问题停止继续调整。

## 已实现的基础

- 不再按 30 个记录日期删掉饮食历史；可通过月历浏览、补记历史日期。14 天图表是显示范围，不是保存范围，统计截止所选日期。
- v5 JSON 完整备份包括 `entries/settings/body/weight/burn/completion/meta`；可恢复空类别、只有设置或身体数据的备份。
- 原有本地存储键不删除。首次保存把现有数据与新增状态一起写入 `kcal.data.v5`，以后从该快照读取；不是每次启动重新从旧键合并。
- 普通保存和恢复都只写一个快照，使用浏览器 `localStorage.setItem` 的原子写入特性；失败恢复上次已保存的内存状态，显示错误，不声称成功。
- 保存前检测其他窗口是否已经更新快照，发现过期页面则停止保存并提示重新加载；导出也要求页面数据未过期。
- 如果检测到读取异常，停止普通保存；可导出 `kcal-recovery-日期.json` 保留原始内容用于排查。这种原始恢复文件不等同于正常备份。应用内自动恢复异常存储仅接受覆盖有效 v5 完整备份。
- 有效旧版 v1–v4 备份继续兼容。覆盖替换文件包含的整类数据；文件缺少的类别保留。合并保留现有饮食，同一天体重/能量由导入值替换，确认界面解释此规则。
- 合并按完整条目内容及重复份数处理；同一餐两份相同食物不丢掉，重复恢复同一文件也不反复增加。
- 恢复前预览日期范围和各类别记录数量；取消或存储失败不部分恢复。
- 导出提示区分“已发起导出”和“文件已保存”。浏览器无法证明用户完成了文件保存，使用者需在文件 App 中确认。

## 无需每日确认的记录与计算

移除每日完成卡片与两个勾选项。饮食保存后直接进入统计，不增加每天确认是否记录的操作；缺失饮食不是零摄入，有条目也不宣称全天已记全。

v5 的旧 `completion` 字段为恢复兼容保留，不再用于计算。手动能量保存记录录入时间，今天标为“今日累计”，历史日期标为“历史录入”；不会因日期已结束就宣称手表数据已全部同步。

- 健康能量路径：活动 + 静息，不另外加入训练热量、活动系数或食物热效应。
- 公式路径：BMR × 活动系数，不再另加摄入的 10%。它是全天公式估算，与健康能量统计分开。
- 今天不展示全天差额；历史日期有饮食与消耗时直接计算记录差额，公式消耗明确标为估算。历史手动能量应录入全天累计，允许补录修正。
- 图表分别显示已记录摄入平均、已录入健康能量平均、同日配对差额及公式估算平均，附实际覆盖天数和可阅读明细。平均值不含今天，缺失日不当成零，说明漏记与部分能量会影响结果。
- 参考摄入使用身体档案的全天公式估算；修正参考下限生效后显示的实际差额，取消按单日差额外推“预计每周减重”，不自动修改用户目标。沿用的摄入下限仅是参考约束，不是个人安全保证。
- 趋势参考使用所选日期截至的近 28 天窗口。至少 4 次称重、跨度至少 14 天，首次称重当天至末次称重前一天每天均有饮食条目；以称重日期作线性回归估计体重趋势。它依赖已记录摄入，漏记会影响结果。该窗口/记录门槛是可用性规则，不是经过临床验证的准确性标准。
- `7700 kcal/kg` 仍是粗略换算，不能消除体重水分、食物估算和代谢适应的误差。趋势结果改称“推算参考”，不称“实际 TDEE”或声称比其他方法更准确。

参考：[FAO 能量需求与活动水平](https://www.fao.org/4/y5686e/y5686e07.htm)、[Apple 活动能量](https://developer.apple.com/documentation/healthkit/hkquantitytypeidentifier/activeenergyburned)、[NIDDK 动态体重模型](https://www.niddk.nih.gov/research-funding/at-niddk/labs-branches/laboratory-biological-modeling/integrative-physiology-section/research/body-weight-planner)。

## 后续设计约束

参考 [Apple HIG](https://developer.apple.com/design/human-interface-guidelines/)，保留系统字体、分组卡片、深浅外观、明确标签和安全区。设置改为不透明的分组页面，顶部保存、独立危险操作。设置、返回、关闭和列表操作使用线条 SVG 图标，去除导航圆形灰底；触摸区域至少 44 × 44 CSS px，键盘焦点可见，设置页管理焦点与背景滚动，并尊重减少动态效果。

暂不引入 Liquid Glass。最新 HIG 工具栏已包含液态玻璃与圆形控件的指导，去除圆底是用户选定的本项目样式，不将其描述为苹果强制要求。参考：[Buttons](https://developer.apple.com/design/human-interface-guidelines/buttons)、[Settings](https://developer.apple.com/design/human-interface-guidelines/settings)、[Layout](https://developer.apple.com/design/human-interface-guidelines/layout)、[Toolbars](https://developer.apple.com/design/human-interface-guidelines/toolbars)。

优先复用本项目已有解析、日历、图表、备份，以及浏览器标准能力；外部组件按实际需求选择，核对 iPhone PWA、离线能力、体积与许可证后再使用，不为复用引入无关的服务器或原生工程。

## 训练与睡眠：建议采用手动与导入并存

本阶段已加入训练、睡眠表单及约定日汇总JSON接收端。下一阶段在iPhone验证真实导出、去重与日期口径，再决定是否接收原始样本或增加更多训练细节。下面是导出端接续方向。

| 数据 | 手动记录兜底 | Apple 健康导入方向 | 建议 |
| --- | --- | --- | --- |
| 睡眠 | 填实际睡眠时长；可选睡醒精神状态 | 快捷指令读取睡眠样本，输出精简 JSON，再在 PWA 选择文件导入 | 优先验证睡眠导入；失败仍可手填，不必逐项抄分期 |
| 有氧训练 | 类型、时长，可选距离、主观强度 | 核验本机快捷指令对体能训练及其详情的读取能力；不把锻炼分钟误当训练清单 | 可先手动快捷记录，原型通过后减少填写 |
| 力量训练 | 动作、组数、次数、重量，可复用上次模板 | 健康训练汇总通常不足以描述每组训练，需要人工补充或专门训练应用导出 | 使用混合方案，健康数据提供会话概况，手动记录训练内容 |
| 主观恢复 | 精神、疲劳、酸痛，可选 | 不推测成设备测量值 | 由本人选择，避免每天填写大量问题 |

### 为什么不能直接承诺网页自动读取

PWA 没有直接调用 HealthKit 的接口。当前 GitHub Pages 没有接收数据的后端；快捷指令生成文件后由网页导入，是减少抄录的路径，不能叫做网页直接读取或已经实现后台自动同步。

苹果官方确认“查找健康样本”可返回睡眠分期：[快捷指令更新说明](https://support.apple.com/en-hk/101583)。但是本机可用动作、健康授权、样本内容、导出文件和 PWA 导入需要 iPhone 实测。尤其训练会话是独立的 HealthKit 数据类型，不能由“能读取健康样本”推断所有训练详情都可读取：[HealthKit 数据类型](https://developer.apple.com/documentation/healthkit/data-types)。

### 睡眠汇总必须解决的口径

1. “在床”和“睡着”分开；不能把在床时长及各睡眠阶段相加。
2. 实际睡眠时长来自睡着的时间区间；同源重叠样本、不同设备来源和粗细睡眠阶段需去重、明确优先级。
3. 夜间睡眠归到醒来的日期；午睡单独标注。保留带时区的开始/结束时间，避免跨午夜或旅行时归错日期。
4. 导入预览显示日期、时长、来源和覆盖范围，与 Apple 健康显示值核对；缺失样本不当成 0 小时。

依据：[Apple 睡眠分类与重叠样本说明](https://developer.apple.com/documentation/healthkit/hkcategoryvaluesleepanalysis)。

### 导入与手动修正的共同规则

- 未来记录保留来源、开始结束时间、原始单位、导入批次和更新时间；手动修正注明来源。
- 同一批文件重复导入幂等，修订日汇总替换旧汇总，不做累加。
- 多设备能量样本不能未经核对直接相加；与健康 App 的日汇总做对照。
- 手动修正和导入冲突时先预览，不静默覆盖本人确认过的数据。
- 训练消耗只展示在会话详情，不重复加入每日活动能量。
- 完整备份随新类别升级版本；旧备份缺少训练/睡眠时继续保留现有对应数据。

## 下一阶段的验证顺序

1. 在 iPhone 核对系统版本、可用快捷指令动作及睡眠健康授权。
2. 同一次导出活动能量、静息能量和睡眠的小 JSON 文件；核对能量是否与健康 App 一致、睡眠时长和日期是否正确。
3. 用一周数据验证跨午夜、重复导入、样本缺失和手动修正。
4. 独立验证训练会话读取；读取不全则保留类型/时长的快捷手填，力量训练仍需要动作记录。
5. 原型通过后再实现正式输入、导入及周复盘页面。界面不要求自动导入先成功才能使用。

### 次日补齐与迟到数据（待实现）

- 当天继续记录饮食；日内健康能量只显示累计与导出时间，不计算全天差额。
- 建议早晨导出一次，默认覆盖最近 7 天及今天，允许选择更长范围补历史；同一 JSON 同时包含前一天能量及前一晚睡眠。
- 能量归属其实际日期，跨夜睡眠归属醒来日期。例如 10 月 8 日早晨导入：10 月 7 日能量补到 7 日，7 日晚至 8 日早晨睡眠归到 8 日。
- 已结束日期的汇总仍可因后续同步而更新；按更新时间处理重复导入，更新原汇总，不累加，不把旧文件覆盖较新的导出。
- 健康状态由文件覆盖范围与更新时间生成；不增加人工完成勾选，不将没有样本当成零。
- 当前静态 PWA 仍需用户选择文件导入；快捷指令生成文件不等于网页后台自动读取。
